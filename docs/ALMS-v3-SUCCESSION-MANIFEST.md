## I. Purpose

This document defines the succession boundary between ALMS_v2 and ALMS_v3.

It:

- declares ALMS_v2 constitutionally sealed,
- establishes the successor conditions for ALMS_v3,
- defines the inheritance rules for v3,
- prohibits reinterpretation of v2,
- prohibits cross-epoch mutation,
- prohibits recursive sovereignty,
- preserves refusal, replay, and provenance across epochs.

This manifest does not create ALMS_v3.

It defines the conditions under which ALMS_v3 may be created.

## II. Successor Position

```text
ALMS_v1 (sealed)
 -> ALMS_v2 (constitutionally sealed)
 -> ALMS_v3 (successor-eligible)
 -> ALMS_v4+ (future successors)
```

ALMS_v3 is:

- not yet instantiated,
- not yet authorized,
- not yet defined.

This manifest defines the rules, not the epoch.

## III. Succession Doctrine

### 1. Upstream Epochs Are Immutable

ALMS_v1 and ALMS_v2 are:

- sealed,
- immutable,
- non-interpretable,
- non-expandable,
- non-recursive.

ALMS_v3 may reference v1 and v2.

ALMS_v3 may not reinterpret v1 or v2.

### 2. Successor Epochs Are Additive-Only

ALMS_v3 may:

- add new surfaces,
- add new invariants,
- add new domains.

ALMS_v3 may not:

- mutate ALMS_v2,
- reinterpret ALMS_v2,
- override ALMS_v2 refusal,
- alter ALMS_v2 dependency ordering.

### 3. Successor Epochs Must Declare Their Own Constitution

ALMS_v3 must:

- define its own constitutional doctrine,
- define its own subsystem enumeration,
- define its own dependency graph,
- define its own invariants,
- define its own extension perimeter.

ALMS_v3 may not inherit v2's constitution implicitly.

Inheritance must be explicit.

### 4. Successor Epochs Must Preserve Core Invariants

ALMS_v3 must preserve:

- refusal sovereignty,
- replay determinism,
- provenance anchoring,
- non-recursive topology,
- additive-only growth,
- non-interpretive behavior,
- authority-bounded execution,
- institutional boundedness.

These invariants are epoch-sovereign and non-negotiable.

### 5. Successor Epochs Must Declare Migration Compatibility

ALMS_v3 must:

- declare v2 -> v3 migration rules,
- preserve cross-epoch replay compatibility,
- preserve refusal boundaries,
- preserve provenance lineage.

Migration must be additive-only.

## IV. Successor Conditions

ALMS_v3 may be instantiated only when:

1. ALMS_v2 is sealed
   already satisfied
2. A successor justification exists
   new domain, new substrate, new constitutional need
3. A successor constitution is drafted
   ALMS-v3-CONSTITUTIONAL-DOCTRINE.md
4. A successor dependency graph is defined
   non-recursive, downstream-only
5. A successor invariants block is declared
   refusal, replay, provenance, authority, extension
6. A successor migration surface is defined
   ALMS-v3-MIGRATION-COMPATIBILITY.md
7. No v2 surfaces are mutated
   strictly enforced
8. No recursive sovereignty is introduced
   strictly prohibited

Only when all conditions are met may ALMS_v3 be activated.

## V. Prohibited Succession Patterns

ALMS_v3 must reject any attempt to perform the following.

### 1. Reinterpret ALMS_v2

- altering v2 meaning,
- altering v2 invariants,
- altering v2 dependency ordering.

### 2. Mutate ALMS_v2

- modifying v2 surfaces,
- rewriting v2 history.

### 3. Create Implicit Epochs

- silent ALMS_v3 creation,
- undeclared successor epochs.

### 4. Generate Authority

- creating new constitutional powers,
- creating new adjudicative surfaces.

### 5. Repair Epoch Drift

- smoothing inconsistencies,
- fabricating continuity.

All such attempts must trigger REFUSAL.

No inferred lineage.

No synthetic continuity.

No narrative repair.
